# StockFlow: Android-кейс для портфолио

## Задача

Сотрудник склада считает товары при нестабильной связи. Изменения должны сохраняться на устройстве, переживать перезапуск процесса и уходить на сервер после восстановления сети. Одновременные изменения с другого устройства нельзя молча перезаписывать.

Проект самостоятельный: учебные товары, локальный backend, собственный код. Приложение не использует закрытые данные работодателя.

## Пользовательский сценарий

Загрузить задание → найти товар камерой или поиском → ввести количество без сети → продолжить после перезапуска → проверить отправку → при конфликте выбрать локальное или серверное количество.

Четыре раздела делают поведение видимым: задания с прогрессом, инвентаризация с расхождениями, очередь отправки с ошибками и отдельное разрешение конфликтов. Вместо набора экранов с заглушками каждый раздел читает актуальные данные из Room.

## Что демонстрирует код

| Область | Решение | Проверяемый результат |
| --- | --- | --- |
| Compose | Управляемое состояние, сохранение черновика, lifecycle, Navigation Compose | Навигация возвращает в открытую инвентаризацию; черновик не зависит от старой композиции |
| Хранение | Room, Flow, миграции, транзакционная очередь | Ошибка вставки операции откатывает количество; данные сохраняются после перезапуска |
| Синхронизация | WorkManager, FIFO, backoff, постоянный UUID | Потерянный ответ приводит к безопасному повтору той же операции |
| Конкурентные изменения | Серверная версия, HTTP 409, явное решение | Второе устройство не перезаписывает первое без выбора пользователя |
| CameraX / ML Kit | Lifecycle, асинхронный анализ, закрытие ImageProxy | Камера освобождается при закрытии; модель распознаёт EAN-13 |
| Проверки | JVM, Room/Compose на эмуляторе, HTTP/SQLite и UI smoke | Ошибки и восстановление воспроизводятся командами |

## Решения и компромиссы

Один Gradle-модуль с пакетами по слоям позволяет сосредоточиться на поведении приложения. Domain не зависит от Android UI или Room. Hilt связывает интерфейсы, Room служит источником локального состояния.

Доставка выполняется с повторениями. Идемпотентный эффект обеспечивает долговечный журнал UUID на сервере, а не обещание exactly-once по сети. Базовая версия фиксируется перед первой отправкой и сохраняется при повторе.

Очередь общая: конфликт головы блокирует дальнейшую отправку, но пользователь продолжает локальный учёт других товаров. Это сознательное ограничение первой версии. Распараллеливание по товару, история успешных отправок и авторизация — возможные следующие этапы.

## Демонстрация на собеседовании

1. Показать задания, поиск и прогресс. Открыть инвентаризацию и фильтр «Не посчитаны».
2. Отключить сеть, сохранить количество и показать операцию во вкладке «Отправка».
3. Перезапустить приложение: значение остаётся. Восстановить сеть и дождаться исчезновения операции после подтверждения.
4. Изменить тот же товар на другом устройстве или через API. Показать сравнение и оба варианта разрешения конфликта.
5. Запустить backend с `--drop-first-response`: сравнить число применённых операций до и после повтора.

## Границы заявления

Это рабочий учебный Android-кейс, а не опубликованная production-система. API 36 и виртуальная камера проверяются локально; реальные устройства требуют отдельной проверки. Код опубликован на GitHub; [CI прошёл на API 26/36](https://github.com/sk784/StockFlow/actions/runs/42071720258), по 35 Android-тестов на каждой версии. Production endpoint, авторизация, серверное разделение пользователей и release-подпись не настроены.
